Knowledge

          

            Roadmap Phase 17 (source §29/§30 — Enterprise Knowledge / Global Intelligence). MobiusX
            Cloud's real EK/GI backends don't exist yet to integrate against (see
            docs/AI_ENGINEERING_PLATFORM_ROADMAP.md's own "genuinely blocked" note on this
            phase) — rather than fake a connection to a system that isn't there, this is a REAL, fully
            local knowledge base: point it at your own folders of docs (an internal wiki export, ADRs,
            coding standards, READMEs — markdown/text), it indexes them on this machine, and relevant
            snippets are retrieved into Build/Spec/Architecture-mode generation prompts automatically
            (see ProjectContext.knowledgeContext) the same way relevant code already grounds
            Build mode. Deliberately global, not scoped to one project — real org knowledge spans projects.

Debug & Fix

          

            Paste a JIRA / Service Desk ticket and get it investigated against THIS project's own real
            evidence — detected routes, database entities, semantic code search, your configured Enterprise
            Knowledge docs, and (when one is running) the live preview's own backend log — then generate a
            fix. This is not a live Jira/Service Desk integration (nothing is fetched by ID,
            nothing is written back) and not cross-service distributed tracing — that needs real observability
            data and MobiusX Cloud. Treat results as evidence-grounded leads, not an automated verdict.

              A terminal command guard (with an optional guarded hold-for-approval mode), a default AI
              model for the Assistant, and a secret scan on outbound task context, all with a shared
              audit trail. This is advisory, single-user governance — not enterprise
              policy management (no multi-tenant auth, no centrally-pushed org policy) and, for the
              terminal specifically, not a security sandbox: anyone with terminal access to this
              machine can bypass it. See docs/ARCHITECTURE.md §12 and the root README.
            


            

              

                
Default AI Model

                
              

              

                Which model the AI Assistant uses when you don't pick one for a specific task (the
                per-task dropdown in Ask/Plan/Build/Spec always overrides this). "Auto" lets the gateway
                choose — a configured Anthropic key first, then a configured free provider, else the
                demo runner. Models greyed out below aren't usable yet — the reason (a missing API key,
                or Ollama not reachable) is shown next to each. See
                apps/cloud-agent-gateway/README.md for how to set up OpenRouter, Groq, or a
                local Ollama install.
              

              

                
                
              

            


            

              

                
Per-Task-Type Model Routing (optional)

                
              

              

                Roadmap Phase 11: route a specific task type to a specific model, overriding the Default
                AI Model above for just that type (a per-task override in the AI Assistant panel's own
                dropdown still wins over both). For example, always send Architecture Generation's larger
                evidence-bundle prompts to a stronger model while leaving routine Ask queries on a
                faster/cheaper one. "Use default" means no rule for that type — it falls through to the
                Default AI Model above, then automatic selection, exactly as if this section didn't exist.

Project Steering (roadmap Phase 16 — §24/§25)

                
              

              

                Real engineering conventions for the CURRENTLY OPEN project — architecture, security,
                API standards, testing — written once under .mobiusx/steering/ and consulted
                automatically by every AI Assistant request (Ask/Plan/Build/Spec/Fix/Database/Architecture/Testing

                because you wrote it.
              

              

              

                
              

              

                
                
              

              
            


            

              

                
Hooks (roadmap Phase 16 — §25, event-driven)

                
              

              

                Hand-authored in .mobiusx/hooks.json at the project root (same one-way-ratchet
                honesty as the Local Agent Permissions section above — a malformed file is ignored in full,
                never partially applied). Two real trigger points: after-api-change fires
                right after Apply writes files whose path matches a rule's pathPattern;
                before-commit fires reactively in the embedded terminal the moment you submit
                a git commit line — same best-effort, not-a-hard-gate caveat the command guard
                above already has for this real PTY. Example file:
                {"hooks":[{"id":"tests-before-commit","event":"before-commit","command":"npm test"}]}
              

              

              

            


            

              

                
MCP Tools (source §28 — Model Context Protocol)

                
              

              

                Real MCP servers (the same protocol Claude Desktop/Claude Code use), hand-configured in
                .mobiusx/mcp.json at the project root and spawned over stdio. When at least one
                server is connected, its tools are offered to Build/Fix-mode tasks (Anthropic runner only —
                see apps/cloud-agent-gateway/README.md for the free-model runners' current gap)
                and the model can call them mid-task. Example file:
                {"mcpServers":{"filesystem":{"command":"npx","args":["-y","@modelcontextprotocol/server-filesystem","."]}}}
              

              

              

            


            

              
Terminal Approval (autonomy level)

              

                "Off" is the reactive guard above: a flagged command still reaches the shell, then gets
                a best-effort Ctrl+C. "Guarded" catches a flagged command's Enter keystroke before it
                ever reaches the shell and holds it until you click Approve or Reject in the terminal
                panel. Same advisory caveat as above — this is not a security sandbox. Changing this
                only affects the terminal's next connection; use "Reconnect Terminal" below to
                apply it to the one currently open.
              

              

                
                
              

              

                
                
              

            


            
            

              
Autonomous Fix Loop (autonomy level)

              

                "Manual" (default) — each Diagnose & Fix cycle's proposed edits still require an
                explicit Apply click, same as any other task. "Auto" — after you click Diagnose & Fix
                the first time, the desktop shell applies that fix, re-runs verification, and (if still
                failing) diagnoses again automatically, up to 3 attempts, then stops and reports an
                honest "still failing" result rather than looping forever. Takes effect on your very
                next Diagnose & Fix click — no reconnect needed.
