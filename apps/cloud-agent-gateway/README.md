# @mobiusx/cloud-agent-gateway

**This is a local reference implementation of the desktop↔cloud task contract (Phase 3) — it is not MobiusX's real production Cloud backend.** It exists so the desktop shell's AI Assistant panel and Tasks view have something real to call, and so the task lifecycle (create → stream progress → persist → resume) is proven out end-to-end rather than mocked in the UI.

It ships with **no credentials and no assumed model**. Out of the box it runs the `demo` runner — deterministic, scripted steps that clearly label every output as non-model-generated. The built-in real providers are supported, each opt-in via its own env var(s): `anthropic` (`ANTHROPIC_API_KEY` + `ANTHROPIC_MODEL`), `openrouter` (`OPENROUTER_API_KEY`, one free-tier model, unverified for build-mode reliability — see below; OpenRouter deprecated its free Llama/Qwen/DeepSeek tier in 2026, and the newer free models that replaced them have their own problems, also below), `groq` (`GROQ_API_KEY`, free-tier models — see below; Groq also moved its Llama models to Enterprise-only and dropped DeepSeek entirely in 2026, so these are OpenAI GPT-OSS and newer Qwen models now, not Llama/DeepSeek — still this gateway's preferred automatic pick over openrouter as of Sept 2026, since these haven't shown OpenRouter's reasoning-loop problem — see registry.ts's AUTO_PRIORITY), `deepseek` (`DEEPSEEK_API_KEY`, DeepSeek's own paid API — the only non-free provider here, never auto-selected, see below), `xkiro`, `apinex`, and `ollama` (no key — a local install, availability checked live against its `/api/tags`). All hosted runners stream token-by-token over the same `/tasks/:id/stream` WebSocket — not buffered until the model finishes.

**Model selection** works like Claude/Cursor: `GET /models` lists every model from every provider, each tagged `available`/`unavailableReason` (a missing API key, or "Ollama not reachable") so an unusable model is shown and disabled, never hidden. The desktop shell lets you pick a standing default in Settings and override it per task in the AI Assistant panel; `POST /tasks` accepts an optional `model: {provider, model}`. Explicit task model > Settings default > automatic selection. An explicitly selected model in Build mode goes directly to that coding provider by default; it does not wait on or depend on Laya. Set `MOBIUSX_BYPASS_LAYA_FOR_EXPLICIT_BUILD=false` to opt back into Laya classification for explicit Build requests. Cloud Auto continues to ask local Laya through Ollama's typed `/v1/systemone` endpoint to classify the workload and complexity; MobiusX maps that decision to a fast, balanced, or powerful tier of configured models. Laya does not generate the answer, and no project text is sent to a hosted router. If Laya is unavailable, MobiusX uses deterministic task-mode rules and continues. The Laya endpoint requires Ollama 0.40+ and `ollama pull laya`. Auto then tries eligible providers in tier order and moves to the next on credit/quota/rate-limit errors or an unrecoverable structured-edit JSON response. Automatic failover never silently selects local Ollama or paid/metered providers. Each switch is shown in task progress and the active provider/model is updated in task history. An explicitly selected model remains pinned and reports its own errors. Image generation is classified separately, but this gateway currently has no image-generation provider. When an explicit/default model is unavailable at task start, `resolveRunner()` (`src/runners/registry.ts`) falls back with an explanatory `TaskSummary.modelNote`.

Greenfield multi-tier Build requests also use a bounded capability pipeline. It checks the scaffold, database/migration, backend/auth, requested business transactions/audit, frontend/API integration, and tests in order; a failed static checkpoint gets at most two focused repairs with its diagnostics. After each stage passes, the accumulated draft is available for inspection; edits are only proposals until the user applies them. A two-hour end-to-end deadline bounds slow CPU-only local inference, and cancellation reaches the active provider. Static gates do not replace compiling/running the applied app; desktop-agent verification and generated-app acceptance tests remain the runtime evidence.

Any task — either runner — can be cancelled mid-flight via `POST /tasks/:id/cancel`. This aborts the runner's actual in-flight work (the Anthropic HTTP request itself for `anthropic`, the scripted timer for `demo`) via a shared `AbortSignal`, not just a UI-side "stop showing this." A cancelled task settles into `status: "cancelled"` — a distinct terminal state from `"failed"`, so the UI and any caller can tell "the user stopped this" apart from "this broke."

"Build" mode never modifies files *itself*, with either runner — this gateway has no disk access at all. Instead it proposes full-file-content edits as structured `ProposedEdit[]` (never a diff/patch — always the complete new file body): the `demo` runner always proposes one clearly-labeled placeholder edit (a `MOBIUSX_DEMO_EDIT.md` that says exactly what it is) so the propose → review → apply pipeline is testable with no model configured, and the `anthropic` runner instructs the model to end its response with a structured JSON block (see `runners/anthropicRunner.ts`'s `EDITS_MARKER`/`parseBuildResponse`) which is parsed leniently and validated — a "modify" is only honored for a path the model was shown in *full* content for, never one it only saw a search snippet of. Either way, these are only ever *proposals*: nothing is written to disk until the user reviews them in the desktop shell and clicks Apply, which calls `apps/desktop-agent`'s `POST /fs/apply-edits` — the human-approval step in docs/ARCHITECTURE.md §8.

**"Spec" mode** is a fourth mode alongside `ask`/`plan`/`build`, for Requirements Engineering. It reuses this exact same edit/review/apply machinery (`MODES_WITH_STRUCTURED_EDITS` in `anthropicRunner.ts` covers both `build` and `spec`) rather than a separate structured-data system, since a generated spec is mechanically just one new markdown file: the model is instructed to produce a fixed section structure (Overview, Functional/Non-Functional Requirements, Constraints & Assumptions, Risks, Gherkin-fenced Acceptance Criteria) under `.mobiusx/specs/<kebab-case-name>.md`, with an explicit "Open Questions" section as the place ambiguity goes instead of the model quietly inventing requirements. The `demo` runner proposes one clearly-labeled placeholder spec (`demo-spec.md`) with that same structure.

**A second-pass Reviewer agent** runs after `build`-mode edits are emitted (never for `spec` or `plan` — see `reviewEdits()` in `anthropicRunner.ts`): a genuine second, independent, non-streaming Anthropic API call with its own "Code Reviewer Agent" system prompt, given the original prompt and the full proposed edits' content, returning `{verdict: "approve" | "concerns", summary}`. `parseReview()` (exported for testing) parses the response leniently but **defaults to `"concerns"`** — never a silent `"approve"` — on any JSON-parse failure or missing/invalid `verdict` field, and the calling code emits an honest `"concerns"` review rather than dropping the review outright if the API call itself fails. The `demo` runner emits a scripted `"approve"` review after its placeholder edit so the reviewer UI (an approve/concerns banner in the desktop shell) is exercisable with no model configured.

**Phase 5:** before any task's `projectContext.relevantFiles` snippets *or full file content* reach a runner, `@mobiusx/secret-scan`'s `scanAndRedact` scans them for secret-shaped text (AWS keys, API keys, PEM private key blocks, hardcoded password assignments, JWTs, GitHub/Slack tokens) and redacts matches in place — so a hardcoded credential that Phase 2's semantic search happens to surface never reaches the Anthropic API call, or the demo runner's echoed context. Redactions are recorded as the task's first step (visible in the AI Assistant panel and Tasks view) and written to the shared audit log (`@mobiusx/audit-log`, `~/.mobiusx/audit.jsonl`). It's a regex scanner, not a real secret-detection engine — no entropy scoring, no provider validation — treat it as a floor, not a guarantee. `apps/desktop-agent` runs the same package's detect-only `scanForSecrets` on generated edit content before writing anything to disk (see its own README) — defense in depth against the model echoing/hallucinating secret-shaped content into generated code.

## Running

```
npm run build -w apps/cloud-agent-gateway
npm run start -w apps/cloud-agent-gateway
# or, for a real model:
ANTHROPIC_API_KEY=sk-... ANTHROPIC_MODEL=claude-... npm run start -w apps/cloud-agent-gateway
```

Prints `MOBIUSX_CLOUD_READY {"port":...,"token":...}` on stdout once listening — this is how the Electron main process (which spawns it automatically) discovers it, the same pattern `apps/desktop-agent` uses.

### Configuring a real model for the desktop app

Exporting provider env vars in your shell only reaches the gateway when you launch it (or `apps/desktop`) from that same shell — running the Electron app from Finder/Spotlight instead of a terminal doesn't inherit those exports at all. For that case, copy `.env.example` to `.env` in this directory and fill in whichever provider(s) you want:

```
cp apps/cloud-agent-gateway/.env.example apps/cloud-agent-gateway/.env
# then edit apps/cloud-agent-gateway/.env yourself
```

- **Anthropic** — `ANTHROPIC_API_KEY` + `ANTHROPIC_MODEL` (not free).
- **OpenRouter** — `OPENROUTER_API_KEY` (get one at openrouter.ai). Unlocks one free `:free`-suffixed model: `inclusionai/ling-3.0-flash-vl:free`. Worth knowing before you reach for it: OpenRouter deprecated its free-tier Llama/Qwen/DeepSeek models in 2026, and the two replacements this gateway tried (Nex-N2.5 Pro and Mini) both turned out to be "reasoning" models that reliably burned their whole token budget on internal chain-of-thought without ever answering, on ordinary build-mode prompts — confirmed live, twice, not a guess. They were removed rather than offered as free options known not to work; Ling 3.0 Flash VL is what's left and hasn't been build-mode-tested either way. See `src/runners/openrouterRunner.ts`'s doc comment for the full history and how to re-verify if this 404s too.
- **Groq** — `GROQ_API_KEY` (get one at console.groq.com). Free tier: `openai/gpt-oss-120b`, `openai/gpt-oss-20b`, `qwen/qwen3.8-27b`. (Groq deprecated its free-tier Llama models to Enterprise-only, and dropped DeepSeek entirely, in 2026 — see `src/runners/groqRunner.ts`'s doc comment for the full history and how to re-verify if these 404 too.)
- **DeepSeek** — `DEEPSEEK_API_KEY` (get one at platform.deepseek.com — a separate signup/billing account, not Groq or OpenRouter). The only **paid** provider this gateway supports: DeepSeek-V4.1-Flash (model id `deepseek-flash`; the old "DeepSeek V4-Flash" name now aliases to this), roughly $0.15-0.30/M input tokens and $0.60-1.20/M output tokens depending on cache hits and UTC peak/off-peak hours (see api-docs.deepseek.com/quick_start/pricing for current rates). Added Sept 2026 at the user's explicit request. Deliberately excluded from `AUTO_PRIORITY` — a metered provider must only ever run when explicitly chosen, never as a silent fallback that starts charging your account. Not yet independently confirmed end-to-end through this gateway (no DeepSeek key was available while wiring it in) — DeepSeek's own docs describe an OpenAI-compatible API, which is what `src/runners/deepseekRunner.ts` assumes; see that file's doc comment if it 400s/404s.
- **Ollama** — no key. The Local picker discovers installed chat models from `/api/tags`, including Qwen2.5-Coder, Qwen2.5 Instruct, and Llama tags; it excludes Laya (used only by the System 1 router) and embedding checkpoints. Duplicate tags with the same digest are collapsed, preferring a specific instruct/quantization tag over `:latest`. Only set `OLLAMA_BASE_URL` if Ollama isn't on the default `http://127.0.0.1:11434`.
- **Long local inference** — Ollama chat uses Node's streaming HTTP transport instead of global fetch's fixed Undici header deadline. `MOBIUSX_OLLAMA_HEADERS_TIMEOUT_MS` defaults to 900000 ms and is capped at 1200000 ms. A complete Build response defaults to a bounded 30 minutes (`MOBIUSX_OLLAMA_BUILD_TIMEOUT_MS`, max 45m) after a measured local build reached 2,237 generated tokens at the old 20m limit without closing its JSON. Staged repair has its own 35m default. `MOBIUSX_OLLAMA_NUM_CTX` keeps one bounded context size (default 12288, range 8192..16384) across requests so Ollama does not repeatedly replace the loaded runner for small prompt-size differences. Successful Ollama responses record prompt/generation counts and Ollama load/evaluation durations when the server returns those fields. `GET /tasks/:id` exposes stage checkpoints after each validated generation gate. `POST /tasks/:id/resume` resumes from the next stage only after validating task requirements, provider/model identity, artifact hashes, project path, and supplied base-file hashes.
- **Laya (System 1 router)** — for local Auto routing, update Ollama to 0.40 or newer and run `ollama pull laya`. Laya is used only through `/v1/systemone` to return typed workload/complexity decisions; it is not added to the chat-model picker and never generates user-facing answers. If Laya is not installed or Ollama does not support the endpoint, Auto continues with MobiusX's deterministic routing rules.

**xKiro** — Set XKIRO_API_KEY in Application Settings. MobiusX exposes Qwen3 Coder Plus through xKiro's OpenAI-compatible endpoint. xKiro advertises 500K free tokens/day (1M/day with its current Telegram verification offer). Requests pass through xKiro and the upstream model provider; this model is not yet phase-tested in MobiusX.

**APInex** — Set APINEX_API_KEY in Application Settings. MobiusX exposes DeepSeek V4.1 Flash through APInex's OpenAI-compatible endpoint. APInex advertises 1M tokens/day for free-category models. Requests pass through APInex and the upstream model provider; this model is not yet phase-tested in MobiusX.

You only need to fill in the provider(s) you actually want — the rest just show up as unavailable (with an honest reason) in the model picker.

`src/index.ts` loads `.env` via Node's built-in `process.loadEnvFile()` on startup — a missing `.env` is silently a no-op (still the demo runner, still "no credentials, no assumed model" by default), and a real shell export always takes precedence over the file if both are present. `.env` is already gitignored so your keys never get committed; `.env.example` itself carries no real values.

### Voice input (AI Assistant page)

The mic button next to the AI Assistant's prompt input (`apps/desktop/src/renderer/renderer.js`'s `createAssistantPanel`) is an add-on way to fill that box, not a separate feature with its own key — it reuses `GROQ_API_KEY` (see above) to call Groq's hosted Whisper endpoint (`POST /transcribe`, `src/voice.ts`). With no `GROQ_API_KEY` set, the button is shown but disabled, with a tooltip saying so — `GET /transcribe/status` is what the renderer checks to decide that, the same honest-availability pattern `GET /models` uses per provider. Electron doesn't ship Chrome's own built-in SpeechRecognition web service, so a browser-only Web Speech API approach reliably fails here — this server round-trip is what actually works.

## Data

Tasks persist to `~/.mobiusx/cloud-agent-gateway/tasks.json` (override with `MOBIUSX_CLOUD_DATA_DIR`) — deliberately outside any project repo, since tasks aren't scoped to one project.

## Swapping in the real backend later

Point the desktop shell at a different base URL that implements this same contract (`packages/protocol/src/cloud.ts`), or adapt this contract to match the real backend's once that integration is scoped — see docs/ARCHITECTURE.md §12.

## Known gaps

- No auth beyond a per-process bearer token (fine for "one local desktop app talking to one locally-spawned process"; not how a real multi-user cloud service would authenticate).
- Cancellation itself is process-local. On startup, persisted queued/running task records are changed to failed with a clear interruption message; a validated staged Build checkpoint is retained and can be continued with `POST /tasks/:id/resume`. Non-staged tasks and tasks without a validated checkpoint must be restarted. The resume request requires refreshed project context and rejects mismatched tracked base-file hashes instead of overwriting changed workspace content.
- The secret scanner is regex-only (see above) — no entropy scoring, no provider-specific validation, and it only covers `relevantFiles` snippets/content, not the prompt text itself or (for the anthropic runner) the model's own output before it's split into prose/edits.
- Build-mode and spec-mode edit parsing (`parseBuildResponse`) is a simple marker + fenced-JSON convention this gateway instructs the model to follow — it's not a guaranteed structured-output mode of the underlying API, so a model that ignores the instruction just yields prose with no edits (graceful, not a crash) rather than a parse failure.
- The reviewer agent is one extra model call with a distinct prompt, not an orchestrated multi-agent workflow — it has no tools, no ability to request changes and re-check them, and no state beyond that single call.
- Voice input is single-shot (record, stop, transcribe) — no live/streaming partial transcription while speaking, and no client-side silence-detection auto-stop; the user has to click the mic button again to end the clip.
- **The second-pass Reviewer is Anthropic-only.** Build-mode edits produced by `openrouter`/`groq`/`ollama` skip it entirely (a note to that effect is appended to the task's output) — review those edits yourself before applying.
- **Neither Groq nor OpenRouter has a free DeepSeek model as of Sept 2026** (Groq dropped its DeepSeek R1 distill entirely; OpenRouter deprecated its whole free Meta/Qwen/DeepSeek tier — see groqRunner.ts and openrouterRunner.ts for the history). DeepSeek-V4.1-Flash is available through this gateway, just not free — see the `deepseek` provider above. Ollama's `deepseek-coder-v2` remains the one local/free DeepSeek-family option.
- **A stale Ollama selection can go stale.** `ollamaRunner.listModels()` reports the exact locally-installed tag (e.g. `qwen2.5-coder:latest`), and `resolveRunner()` matches a Settings default/per-task request against that exact string. If you re-pull a model under a different tag suffix, a previously-saved selection no longer matches and falls back to `demo` with a generic "not available right now" note rather than fuzzy-matching to the new tag — deliberate, to keep the "always tell the truth about availability" contract simple; re-pick the model in Settings/the picker if this happens (see `src/runners/ollamaRunner.ts` and `test/registry.test.ts`).
